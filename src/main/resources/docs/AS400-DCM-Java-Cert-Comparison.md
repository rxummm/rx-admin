# AS400 (IBM i) 环境中 DCM 证书与 Java 运行环境证书对比及适用场景规范说明书

在 AS400 (IBM i) 系统运维中，通过 **DCM (Digital Certificate Manager)** 安装证书与直接在 **Java 运行环境 (IBM JDK)** 的信任库（cacerts）下安装证书，有着本质的区别。它们分别管理着完全不同的系统层面，且安全信任的流向正好相反。

---

## 一、核心区别对比

| 对比维度 | 通过 DCM (Digital Certificate Manager) 安装 | 在 Java 运行环境 (IBM JDK cacerts) 下安装 |
|---|---|---|
| **底层物理存储位置** | 存储在 IFS 文件系统的系统集成密码库中：`/QIBM/UserData/ICSS/Cert/Server/DEFAULT.KDB` | 存储在各个指定 JDK 版本的安全目录中：`/QOpenSys/QIBM/ProdData/JavaVM/jdk80/64bit/jre/lib/security/cacerts` |
| **系统主要角色** | 服务端 (Server) | 客户端 (Client) |
| **安全信任的方向** | **"让别人信任我"**：向外部客户端发送 AS400 本身的证书，用于证明 AS400 自身的合法身份。 | **"我去信任别人"**：让 AS400 内部运行的 Java 程序去校验并信任来自外部第三方服务器的证书。 |
| **影响的系统服务** | 控制 AS400 自身的系统级主机服务（如 Signon 登录服务、Database 数据库通道、HTTP 网页服务器、FTP 等）。 | 仅控制运行在 AS400 内部、基于 Java 虚拟机 (JVM) 启动的业务系统、中间件、应用或代码脚本。 |
| **首选管理工具** | 2001 端口的网页管理界面（HTTP 管理器）、`CHGDCMPWD` 等系统命令。 | Java 开发套件自带的命令行工具 `keytool`（需在 Qshell 环境下运行）。 |
| **重启生效对象** | 通常需要重启 AS400 主机服务器：`ENDHOSTSVR SERVER(*ALL)` / `STRHOSTSVR` | 必须重启运行该段代码的 Java 应用进程、WebSphere (WAS) 实例或 Tomcat 容器。 |

---

## 二、详细原理解析

### 1. 为什么要在 DCM 中安装证书？（处理**"进站"**请求）

当技术人员从个人电脑打开 ACS 客户端登录 AS400、使用 Excel 通过 ODBC 链接大机抽取数据，或者通过浏览器访问 AS400 的 2001 导航面板时，**AS400 扮演的是服务器的角色**。

- **运作机制**：当你在本地 ACS 勾选了"使用 SSL 安全连接"并点击登录时，AS400 的登录守护进程（`*SIGNON`）会立刻前往 DCM 的 `*SYSTEM` 证书库中抓取管理员为其分配的数字证书，并将该证书的安全公钥发送给你的个人电脑。你的电脑在验证该证书合法后，双方成功建立起加密的握手通道。
- **核心结论**：凡是解决**"外部客户端（如 ACS、第三方系统）连接 AS400 报错拒绝"**的问题，必须在 DCM 中操作。

### 2. 为什么要在 Java 运行环境 (JDK) 中安装证书？（处理**"出站"**请求）

当 AS400 内部运行了一段 Java 业务代码（例如：ERP 系统需要定时去调用外部银行的 HTTPS 支付接口，或者去对接外部税务局的 Web Service 加密接口）时，**AS400 扮演的是客户端的角色**。

- **运作机制**：AS400 内部的 JVM（Java 虚拟机）在向外发起 HTTPS 请求时，为了防止中间人攻击，它会强制去读取它自身 JDK 目录下的安全信任库 `cacerts`。如果目标银行或税务局接口的 CA 根证书不在这个 `cacerts` 文件中，Java 环境出于安全考虑会直接强行熔断连接，并在后台抛出典型的 `javax.net.ssl.SSLHandshakeException` 异常。
- **核心结论**：凡是解决**"AS400 内部程序主动向外发送请求、调用接口报握手失败"**的问题，必须使用 `keytool` 写入对应 JDK 的库中。

## 三、典型适用场景列举

### 💡 场景 A：必须使用 DCM 安装的场景

1. **ACS 客户端安全登录**：新合规要求所有运维人员在通过 ACS 客户端连接 AS400 时，登录界面必须勾选 SSL 加密通信。
2. **数据库加密传输 (ODBC/JDBC)**：外部高层业务系统（如数据中台、商业智能 BI）需要通过加密端口（如 `9471` 等）使用 JDBC 安全读取 AS400 上的 DB2 数据库表。
3. **AS400 网页端强加密 (HTTPS)**：通过浏览器访问 `http://<IP>:2001`（Navigator for i）时，浏览器提示不安全。需要将合规的公网域名证书导入 AS400 并绑定到对应的内置 HTTP Server，使其支持 `https://` 访问。
4. **对象/程序签名 (Object Signing)**：公司发布的操作系统补丁、重要程序对象（`*PGM`）在分发到其他系统前，需要使用证书进行电子签名以防被篡改。

### 💡 场景 B：必须使用 Java 环境 (keytool) 安装的场景

1. **AS400 消费外部 Web Service/API**：AS400 内由 Java 开发的中间层程序，需要通过 HTTPS 协议定时调用外部三方供应链系统的 RESTful 接口。
2. **发送加密邮件 (SMTP over SSL/TLS)**：AS400 内部的 Java 邮件警报插件，需要连接公司统一的加密邮件服务器（如 Microsoft 365 端口 587/465）发送生产异常报警邮件。
3. **WebSphere (WAS) / Tomcat 应用信任链扩展**：部署在 AS400 WebSphere 中间件上的大型 Java 业务系统，需要与另外一台服务器的底层组件进行安全的 RMI 或 HTTPS 内部通讯，需要将对端服务的自签名证书注入 JDK。

---

> **提示**：如果您在业务中遇到具体的连接案例，不确定应该在哪个层面配置证书，可以提供发起方与接收方的身份，便于进一步做架构诊断。
